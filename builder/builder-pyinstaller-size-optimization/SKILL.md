# PyInstaller 打包体积治理

## 目标与适用范围

将 Python 项目打包为可交付程序时，在**功能完整、目标平台可运行、开发环境不受损**的前提下，减少无关模块、二进制文件、插件及资源。支持 macOS、Windows 等平台；平台特有的文件结构和签名要求分别验收。

PyInstaller 既不是将整个 Python 环境原样复制，也不能保证只收集业务代码真正执行的文件。其导入图、动态导入补充、依赖 Hook、共享库和数据文件收集都可能放大产物。

> [!important]
> 优先修正打包配置，**不得通过 `pip uninstall`、`conda remove`、升级或改写当前环境中的第三方库来缩包**。不得为此破坏共享组件生产代码或删除功能。用户明确授权另建隔离环境时，另作处理。

## 一、确认边界及建立基线

1. 确认程序入口、目标操作系统与 CPU 架构、Python 解释器、环境管理器、PyInstaller 版本、打包模式、应用图标和运行所需资源。
2. 读取原有 `.spec`、构建日志及构建目录，不要仅凭 `requirements.txt` 或当前环境已安装的库推断最终体积。
3. 记录旧产物的实际大小、文件数、构建参数、签名或架构检查结果，以及已被真实验证的功能。区分 `.app` 本体、同名普通文件夹和 `build/` 中间文件，防止重复占用硬盘。
4. 明确用户对旧版的保留要求及磁盘空间上限。若要求先删除旧版，**必须先记录基线、确认目标路径和潜在失败代价**；不得把其他项目的产物一起删除。
5. 对压缩包大小、`du` 显示的磁盘占用、文件逻辑大小和 APFS 克隆/符号链接分别说明口径；不要混用数值。

## 二、定位大型依赖如何进入产物

优先检查：

- 构建日志和 `--log-level=DEBUG` 可见的收集信息。
- `build/<应用名>/xref-*.html`：追溯 Python 模块导入图。对数据文件或原生动态库，另结合 Hook、二进制依赖和 `.toc` 清单追踪。
- `Analysis-00.toc`、`PYZ-00.toc`、`COLLECT-00.toc` 等实际存在的清单；`warn-*.txt` 可用于核查缺失导入，不代表体积来源的完整清单。
- 项目入口及其递归导入的自有组件、`TYPE_CHECKING` 导入、延迟导入、插件注册、`importlib` 调用，以及外部依赖的 Hook。

对每项大型文件或依赖建立证据链：**产物位置与体积 → 由哪个模块或 Hook 收集 → 业务运行时是否需要 → 排除依据 → 验证结果**。

区别：

- **必需**：已在真实业务路径使用，或实际运行证明必须保留。
- **可疑**：因为公共模块、可选集成或宽泛 Hook 被收集，尚未证明必需。
- **可排除候选**：经导入图和功能范围查证与当前应用无关；仍须通过重新打包验收才能定案。

QtWebEngine、Qt Quick/QML、Qt PDF、Qt Multimedia、NumPy/OpenBLAS、SciPy、Rasterio/GDAL、PyProj、GeoPandas、Shapely、CuPy/CUDA 等**只能作为重点排查对象，不是通用黑名单**。

## 三、逐层精简

1. 首选在 `.spec` 的 `Analysis(excludes=[...])` 中排除经查证无关的 Python 模块；命令行构建可用 `--exclude-module`。使用已有 `.spec` 构建时以其中的分析配置为准，不假设额外命令行参数都会覆盖它。
2. 检查第三方 Hook 是否添加了 `hiddenimports`、`datas`、`binaries`，或使用 `collect_all()` 等宽泛收集方式。必要时在项目专用 Hook 或 Hook 配置中作有依据的最小化处理。
3. Python 模块剔除后，若仍残留无关原生库、Qt 插件或资源，才基于明确的归属与依赖关系精细过滤。不得机械删除 `.dylib`、`.so`、`.dll`、`.framework` 或整个 `plugins/` 目录。
4. 保留程序实际使用的动态导入、异步驱动、证书/字体/图标/主题、Qt 平台插件、模板和离线前端资源。不能仅凭静态代码没出现导入语句就判定无用。
5. 处理 `sitecustomize.py`、环境变量及开发机 DLL/动态库搜索路径时，确认它们在冻结程序中的真实行为；如需运行时初始化，用有依据的 PyInstaller 运行时 Hook，不假定开发环境补丁自动生效。
6. 每轮只改变一组有明确依据的收集项，记录减少的文件、大小、失败现象与回退措施。遇到功能倒退，首先恢复相关项并追查，而非删减功能。

> [!warning]
> PyInstaller `--onefile` 不是依赖精简的替代品：它可能在启动时解包，改变启动速度和运行时磁盘需求。macOS 图形应用通常优先考察 `--onedir` 配合 `--windowed` 的 `.app`。不要通过压缩或不显示文件来虚报真实空间节省。

## 四、打包、验收与硬盘管理

- 构建前核对输出目录，不覆盖源码、其他应用或不明产物；避免在 Git 常驻 `dev` 等受保护工作区直接修改生产代码。需要修改仓库打包配置时，服从项目 Git / Worktree 规范。
- 用户要求**单版本保留、生成前删除旧版**时：先记录旧版基线及清理目标，确认旧版属于该任务、目录无其他应用，再删除旧应用与确认无用的重复产物；明确新构建失败可能暂时无可运行版本。不得擅自删除用户数据或全局缓存。
- 用户未要求提前删除旧版时：优先在隔离输出位置构建并验收，完成后再替换旧版；不长期并存多个巨型版本。删除仅针对已核实的构建产物。
- 对应用**实际启动**并执行关键场景：启动与退出、主要界面和交互、文件读写、网络与手机端通信、动态导入、打包的离线资源、端口释放、重复启动、异常提示及权限等。
- macOS 检查目标架构（例如 ARM64）、应用图标、`Info.plist`、签名和动态库加载；适当使用 `file`、`codesign --verify` 检查，但**签名校验通过不代表用户交互功能验收通过**。
- 自动化无法点击原生窗口或连接真实设备时，逐项标记“未实测”，不可拿单元测试、服务健康检查或静态扫描冒充人工窗口验收。
- 完工清理本任务确认无用的 `build/`、重复普通目录、失败 `.app`、临时草稿和输出副本；清理前确认文件归属及用户数据边界，禁止无范围删除或误删源文件。

## 五、终止条件与交付报告

同时满足以下条件即可停止，不追求持续降到某个任意体积阈值：

- 必要功能及目标环境的验证达到已约定范围，未通过和无法验证之处明确披露。
- 无关大型依赖有证据地排除；剩余大头属于当前软件功能所需，或继续优化的收益不足以覆盖风险和工时。
- Python 开发环境和共享组件未受破坏；最终构建文件与磁盘占用符合用户保留策略。

报告应包含：

1. 入口、平台、构建配置及实际执行的测试范围。
2. 旧版与新版的体积（标明 MiB/MB 口径）、文件数、减少比例与输出路径。
3. 剔除项及其收集来源、确认仍必需的前十大体积项。
4. 真实启动、GUI、联网/离线、文件写入、动态依赖和退出的验证结果；如有未测项目，如实标明。
5. 旧版与重复目录清理结果、构建中间文件处置、磁盘实际剩余占用及遗留风险。

## 实际案例：接力打字板（2026-10）

一次 macOS ARM64 PyInstaller 构建从约 **809.2 MiB／4,390 文件**，优化到约 **107.4 MiB／416 文件**，分别减少约 **86.7%** 和 **90.5%**。该案例的主要膨胀源涉及 QtWebEngine、NumPy/OpenBLAS、Rasterio/GDAL、PyProj 等与该应用功能无关的收集链。

其关键做法是先调查公共模块间接引用及 Hook，再精确排除，保留必要的 Qt、主题和 Socket.IO `threading` 驱动，最后实际启动并联调。项目报告记载 46 项仓库测试通过，手机页面、同步与草稿保存得到验证；原生桌面窗口的人工视觉操作未完成，**不得据此宣称全部 GUI 已实测**。

此结果仅证明该项目的有效实践，不承诺其他程序也能缩至类似大小。达到约 107 MiB 且用户认为可接受后即应收口。
