# Python 通用规范

## 适用范围

只要任务涉及 Python 代码的创建、修改、重构或 review，就应遵守本 Skill。局部目录若有更具体的 `AGENTS.md` 或专业 Skill，则在本规范基础上继续叠加。

## 中文化

- 项目自有类、函数、方法、变量、注释、控制台输出和日志，默认使用简体中文。
- Python 保留字、标准库/第三方库真实 API、第三方基类要求的重写方法名和参数名必须保持原样。
- 对第三方 override 不得为了中文化改方法名、参数名，也不得强行添加本仓库自定义参数前缀。

## 脚本结构

Python 文件通常按以下顺序组织：

- `# ◑ 导入`：所有 import。
- `# ◕ 功能`：类和函数定义。
- `# ◍ 运行`：仅在确有直接运行代码时存在，通常包含 `if __name__ == "__main__":`。

规则：

- `# ◍ 运行` 实际为空时，不得保留这个标题或空的 main 区域。
- 从同一模块导入超过三个对象时，使用括号换行形式提高可读性。
- 通常一个脚本只保留一个主要 class，避免堆叠多个职责不同的 class；少数纯入口脚本可以没有 class。
- 在适合由 class 组织职责的模块中，优先使用 class 内方法（包括合适的静态方法）承载逻辑，避免散落大量独立函数。
- 不要因为历史文件格式不同就复制旧格式；修改或新建代码时以当前规范为准。

完整脚本骨架与 class 范例见 `references/class-script-format.md`。

## Class 与公开 API

- 项目自有 class 名称应以 `_类` 或 `_基类` 结束，便于 import、搜索和类型提示时快速识别类对象。
- class 内部优先通过 `self` 管理共享状态，避免把本应属于实例状态的数据反复作为方法参数传递。
- 大方法应拆分为职责清晰的小方法。
- 对外公开的方法使用 `api_` 前缀，例如 `api_读取_当前值`，让调用方能快速区分稳定入口与内部实现。
- 当一个方法的显式入参数量不少于三个时，每个参数单独一行，保持排版清晰。
- class 应有多行 docstring，说明功能并保留“更新日志”。更新日志日期使用 `YYYY.MM.DD`，每条更新日志必须保持单行，禁止把同一条日志拆成多行。这里不仅是排版偏好：仓库中的自动程序会解析该结构，跨行日志可能导致解析失败。
- 参数或返回值只有在名称与类型仍不足以表达含义时才补充说明；不要重复显而易见的信息。

## 参数命名与类型提示

- 除 `self`、`cls` 以及第三方 override 的既定参数外，方法和函数入参默认使用 `arg_` 前缀，例如 `arg_源字典`。
- `arg_` 的意义是标出“数据从调用入口进入此方法”，帮助阅读者快速识别数据来源和流向；它不是普通变量前缀。
- 使用 `arg_` 的参数必须有明确类型提示。
- 禁止把类成员命名为 `self.arg_...`；入参赋值到实例成员后，该成员已经是对象内部状态，不再是 argument。
- 每个 def 的入参都应提供有意义的类型提示。能够使用具体项目类型时，不要退化成宽泛父类。
- 禁止用 `Any` 或 `object` 充当偷懒的伪类型提示。只有外部接口真实契约本身无法更精确时，才按外部契约处理。
- 多种合法类型使用明确的 `Union[...]`、`Optional[...]` 或代码库当前采用的等价精确写法。
- 为避免循环引用，可以用字符串形式的前向类型引用，例如 `arg_对象: "目标_类"`。
- 绝对禁止为了让 Pyright 等静态检查通过而加入会改变运行时行为的 `assert`。
- 第三方基类的 override 必须忠实保留第三方定义的方法名和参数名。例如 PySide6 的 `keyPressEvent(self, event)` 不应改成 `arg_event` 或中文参数名。

## `__init__.py`

- 默认保持 `__init__.py` 为空。
- import 应直接指向正式定义所在脚本，不通过 `__init__.py` 做无必要的 re-export、兼容转发或入口包装。
- 这样做是为了让大型单体仓库中的真实定义位置保持显式，减少额外转发层与隐式入口。

## Fail Fast 基本原则

本仓库优先暴露错误，反对通过静默默认值、试探性反射和吞异常把错误隐藏到后续流程。

- 字典读取默认不要使用 `.get()` 掩盖缺失字段，应让不符合预期的 Schema 尽早暴露。
- 项目自有稳定对象契约中避免用 `hasattr()` / `getattr()` 试探属性是否存在；如果反射本身是第三方框架、插件协议或动态对象模型的正式机制，则按真实协议使用。
- 禁止 `except Exception: pass`、记录后静默继续等吞异常行为。
- 当前层无法正确恢复异常时，让异常自然上抛；如果捕获只是为了增加上下文，处理后必须重新 `raise`。
- 只有存在明确、业务正确且不会破坏数据一致性的兜底方案时，才允许捕获特定异常后继续。
- 只治理当前任务直接涉及的技术债，不要求一次任务顺手清扫全仓库。

当任务涉及异常处理、字典默认值、兼容逻辑、`.get()`、`hasattr()`、`getattr()`、吞异常、鸵鸟代码扫描或 Fail Fast 专项清理时，继续阅读 `references/fail-fast.md`。

## 控制台输出

新增或修改 `print()`、控制台状态信息或同类日志格式时，继续阅读 `references/console-output.md`。不要自行发明新的中括号状态标签。
