# Fail Fast 与避免鸵鸟代码

本参考用于异常处理、字典访问、反射式试探、兼容兜底和鸵鸟代码专项审查。核心目标不是让程序“更容易崩”，而是让不满足契约的状态尽早、明确、可定位地暴露。

## 核心思想

本仓库偏好显式契约而不是隐式妥协。对于本应存在的数据或接口，直接暴露契约错误通常优于静默返回一个“看起来还能运行”的默认值。

Fail Fast 不是“遇到任何异常都故意崩溃”，而是拒绝在**不知道如何正确恢复**时假装恢复成功。

## 字典访问

- 默认禁止用 `.get()` 为本应存在的键提供静默默认值。若 Schema 规定字段必须存在，应使用 `[]` 直接索引。
- 同样不要用连续 `.get(..., {}).get(...)` 把结构错误伪装成正常缺省状态。
- 大量散落的深层硬编码索引也会腐化。稳定业务 Schema 应优先通过专门的数据访问 API、管理类或原子读写接口集中访问。
- 如果“缺失”本身就是合法业务状态，可以建立显式、安全的读取 API。该 API 必须清楚定义默认值语义、返回类型和必要的诊断信息，而不是把 `.get()` 当作习惯性保险。

### 不要用 `.get()` 隐藏 Schema 错误

如果 `名称` 是强制字段：

```python
名称 = 数据["名称"]
```

比下面这种写法更符合本仓库习惯：

```python
名称 = 数据.get("名称", "")
```

后一种写法会把“上游没有按 Schema 提供名称”伪装成一个合法的空字符串，错误很可能在更远的地方才表现出来。

### 也不要把深层硬编码散得到处都是

Fail Fast 不意味着鼓励整个仓库充斥：

```python
值 = 数据["第一层"]["第二层"]["第三层"]
```

当同一个结构被大量业务代码访问时，应把索引集中到数据管理 API 中：

```python
def api_读取某个_ID_的值(
    self,
    arg_字典: dict,
    arg_ID: int,
) -> str:
    return arg_字典["第一层"]["第二层"][arg_ID]
```

这样底层 Schema 调整时，只需要修改集中管理位置，而不是全仓库追逐字符串键。

### 合法默认值必须有业务语义

如果“字段不存在”本身就是合法状态，可以建立专门 API：

```python
def _安全读取_字典值(
    self,
    arg_字典: dict,
    arg_键: str,
    arg_默认值: str | None = None,
    arg_描述: str = "未知",
) -> str | None:
    if not isinstance(arg_字典, dict):
        print(
            f"[警告] 读取 '{arg_描述}' 时目标不是字典，"
            f"使用默认值: {arg_默认值}"
        )
        return arg_默认值

    if arg_键 in arg_字典:
        return arg_字典[arg_键]

    print(
        f"[信息] 读取 '{arg_描述}' 时键 '{arg_键}' 缺失，"
        f"使用默认值: {arg_默认值}"
    )
    return arg_默认值
```

这和随手写 `.get()` 的区别在于：**缺失是被显式设计、显式命名、显式诊断的业务状态**。不要为了“程序不报错”而滥用这种包装。

## 避免试探性反射

- 对项目自有且契约稳定的类，避免使用 `hasattr()`、`getattr()` 通过字符串试探属性。
- 字符串属性名难以被 IDE 自动重构，容易在类成员改名后悄悄腐化。
- 如果反射确实属于第三方框架、插件协议或动态对象模型的正式机制，应明确说明这是协议要求，而不是把试探当作普通容错手段。

反模式：

```python
if hasattr(对象, "旧属性名"):
    值 = getattr(对象, "旧属性名")
```

如果 `旧属性名` 是项目自身稳定契约，重构工具往往无法追踪字符串中的属性名；几个月后这里可能静默变成一段腐化代码。

## 异常处理

- 原则上先问：当前层是否真的有能力恢复这个异常。没有恢复能力就不要随意捕获。
- 绝对禁止 `except Exception: pass`、裸捕获后返回空值、打印一句警告后继续执行等静默失败。
- 为了补充调试上下文而捕获异常时，输出应具有足够特异性，随后必须重新 `raise`。
- 只有当前层能够提供业务正确、契约明确且不会破坏数据一致性的替代方案时，才允许捕获具体异常并继续。
- 不要为了“把所有分支写满”而制造空 `else: pass`。没有处理逻辑的分支直接省略。

### 最典型的鸵鸟代码

```python
def 某方法(self, arg_参数: int) -> str:
    输出 = ""
    try:
        输出 = str(arg_参数)
    except (SyntaxError, UnicodeDecodeError):
        pass
    except Exception:
        pass
    return 输出
```

这里最严重的问题不是用了 `try`，而是失败后仍返回一个看似正常的值。真实错误被吃掉后，调用方会继续处理错误状态，最终把问题传播得更远。

### 只增加上下文时必须重新抛出

允许：

```python
try:
    self._执行_关键步骤()
except ValueError:
    print("[错误] class 示例_类 -> def _执行_关键步骤 收到非法数据。")
    raise
```

不允许：

```python
try:
    self._执行_关键步骤()
except ValueError:
    print("[警告] 执行失败，继续运行。")
```

除非当前层真的有一个被业务定义为正确的恢复路径，否则“打印之后继续”仍然只是换了形式的吞异常。

## 条件分支也可能是假容错

以下写法没有任何意义：

```python
if not 成功:
    print(f"[警告] 某动作 {动作ID} 失败: {消息}")
else:
    pass
```

直接删除空的 `else` 即可。不要为了让结构“完整”而制造没有语义的分支，也不要在高频成功路径强行打印日志。

## 兼容性与 Fail Fast 的边界

Fail Fast 不等于拒绝兼容，而是拒绝含糊的兼容。

- 优先修复过时调用方、错误 Schema 或不一致的数据源，让系统逼近理想契约。
- 确实需要兼容旧数据时，兼容逻辑必须有明确边界、可观测行为和具体的恢复策略。
- 低频或外部输入场景可以使用 `try...except`，但不得无声吞掉无法恢复的异常。
- 默认值必须表达真实业务语义；不能仅仅因为“这样程序不会报错”就存在。

判断一个兼容层是否合理时，至少要能回答：

1. 被兼容的旧输入或旧调用方是什么？
2. 这种旧状态是否真实存在，而不是凭空猜测？
3. 兼容逻辑什么时候可以删除？
4. 兼容失败时是否会明确暴露？
5. 继续执行是否会污染数据或隐藏更严重的问题？

答不出来的“兼容”通常只是鸵鸟代码。

## 旧代码治理

- 仓库历史代码中仍可能存在大量 `.get()`、`hasattr()`、`getattr()` 和吞异常写法，它们不是新代码的教材。
- 与当前任务无关的历史债可以暂时保留，避免无边界扩大 scope。
- 当前任务直接涉及的代码应返回符合现行规则的新版本，逐步把技术债从活跃区域清除。

## 审查问题

看到一个兜底或异常捕获时，至少回答以下问题：

1. 这里缺失/失败是否真的是合法业务状态？
2. 当前层是否有能力恢复？
3. 默认值是否具有明确业务意义，而不是为了不报错？
4. 如果继续执行，是否可能把错误状态传播到更远处？
5. 如果代码依赖字符串属性名或动态字段，是否会破坏 IDE 重构和长期维护？
