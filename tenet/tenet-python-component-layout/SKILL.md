# Python 内聚组件的局部组织规范

## 核心原则

保持入口明确、组件根目录收敛、内部按职责分层。积极使用有语义的目录嵌套，让共同实现一项功能的文件集中归属；每增加一层目录，都应表达真实职责或边界。

本规范中的“组件根目录”是某个内聚组件的局部根目录，不是仓库根目录。“入口”是供调用者使用或装配组件的主要脚本，不等同于独立运行的启动脚本。

## 组件根目录

- 默认保留一个名称明确的主要入口脚本，使阅读者能直接判断从哪里使用组件。
- 将其他实现脚本放入按职责命名的次级目录，尽量避免与入口脚本大量平铺。
- 组件需要拆分时，入口以必要的装配、协调和对外访问为主，业务实现放入对应职责目录。不为凑齐入口形式增加纯转发文件。
- Python 包机制、命令行或框架约定确实需要的文件可以保留，例如 `__init__.py`、`__main__.py`。这不构成多个业务入口。
- 同一组件有多个正式公开契约时，应说明各自的使用场景；不要把独立子功能强塞进同一个入口对象。

## 内部目录

- 根据共同职责、共同变化原因和依赖关系分组，目录名应说明其中的文件共同负责什么。
- 进入次级目录后仍按相同原则组织。若其中已经出现多个独立职责，继续拆分；不要把根目录的混杂原样搬进一个庞大的 `impl`、`utils` 或“其他”目录。
- 在同一职责已经清楚的叶子目录中，允许保留多个紧密相关的脚本。不要求每个目录都只有一个脚本，也不要求每一层都有入口文件。
- 文件数量不决定目录是否合理。一个文件可以属于独立职责目录；多个文件也可以共同构成一个叶子目录。
- 不为每个文件机械创建同名目录，不建立没有新增语义的多层包装，不为尚未出现的需求预建空层级。
- 简单组件能由一个脚本清楚表达时，保持简单；不设置统一的最少层数、最多层数或每层文件数量。
- 内部组件之间优先通过明确契约协作，避免为取得内部对象而在运行时反向导入装配入口，形成循环依赖。

## 公开契约与内部实现

- 目录嵌套表达归属，不自动形成访问控制。先识别常规调用入口、正式扩展接口和私有实现，再判断某条导入是否越界。
- 常规调用使用约定入口；框架明确支持的基类、协议、数据类型和注册接口，可以从其正式定义脚本直接导入。
- 不因路径含有 `impl` 就否定已经存在的正式扩展契约，也不把全部内部对象重新导出为公共 API。
- 按 `tenet-python-general` 保持 `__init__.py` 默认留空，直接导入正式定义脚本，不增加无必要的 re-export、兼容转发或入口包装。
- 按约定向调用方返回的控制器、适配器等对象，其公开方法同样属于对外契约；不能因对象定义在次级目录中就任意改动。

## 现有组织示例

`SiliconYC/vitro_union_lab` 仓库 `dev` 分支（大分支）中的 `B_底盘/ceno/m2610/B_项目级/B_功能/有界面/x100_项目主界面/` 展示了这一组织方式：

| 相对位置 | 组织作用 |
| :--- | :--- |
| `bc_项目主界面_入口.py` | 组件主要入口，负责装配与对外访问 |
| `impl_功能/A_管理/` | 集中组织适配器、组装工厂 |
| `impl_功能/C_交互/` | 集中组织界面、控制器、快捷键集成 |

借鉴其入口和职责分组，不机械复制目录名称、文件数量或嵌套深度。该组件中的部分基类属于框架扩展接口，不能将次级目录中的所有脚本一概视为私有。

## 调整与审查

1. 阅读现有入口、调用方及局部约定，确认组件边界和公开契约。
2. 按职责归类文件；仅在分组能改善定位、归属或依赖关系时增加层级。
3. 迁移已有文件前，查找普通导入、字符串形式的动态导入、注册配置及资源路径；保留必要公开契约，或在获准变更契约的任务中同步修改调用方。
4. 改动涉及 Python 代码时，按 `tenet-python-testing` 验证受影响行为；测试位置遵守目标仓库现有规范，不照搬示例中的测试目录。
5. 只调整本次任务涉及的组件，不以统一目录外观为由批量迁移全仓库。

审查时重点确认：入口是否一眼可辨、每层目录是否有明确语义、相关文件是否集中、依赖方向是否合理、公开契约是否保持清楚。不要用“根目录只能有一个 `.py`”或“嵌套越深越好”代替这些判断。
