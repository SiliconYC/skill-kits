# 面向 AI 的代码注释

## 核心原则

代码注释的主要价值不是把代码翻译成自然语言，而是保存**无法仅从代码本身可靠推导出的上下文**。

当任务明确要求清理冗余注释、判断哪些历史注释必须保留，或处理连续多行注释、更新日志折行等格式问题时，继续阅读 `references/redundant-comment-cleanup.md`。

优先记录：

- 为什么采用当前设计；
- 架构决策的初衷；
- 特定业务规则或现实约束；
- 为规避已知缺陷而采取的折衷；
- 性能、兼容性或外部接口限制；
- 后续维护者如果擅自“简化”代码会破坏什么。

这些信息能够防止后续 Agent 在重构、补全或清理代码时，因为只理解“代码做什么”却不知道“为什么必须这样做”而破坏原有设计。

## 避免翻译代码

不要逐句把代码语法改写成自然语言。

例如，这类注释通常没有价值：

```python
# 将 x 右移 1 位，并与掩码进行按位与
x = x - ((x >> 1) & 0x55555555)
```

代码本身已经完整表达了这个动作。把语法再说一遍只会：

- 增加信息噪音；
- 占用上下文；
- 在代码修改后更容易腐化；
- 稀释真正需要保存的设计背景。

即使代码很冷僻，也不要只解释每个运算符在做什么。

更有价值的是：

```python
# 使用 SWAR 算法计算汉明重量。
# 保留这种写法是为了规避该高频路径中更直观实现的性能瓶颈。
x = x - ((x >> 1) & 0x55555555)
```

这里保存的是**算法意图和采用它的原因**。

## 注释应该提供增量信息

写注释前先问：

> 删除这条注释后，仅阅读代码、类型提示和命名，维护者是否仍能可靠知道这条信息？

如果答案是“能”，通常不必写。

如果答案是“不能”，尤其涉及业务背景、外部限制、历史原因或不可见约束，就应该写。

## 不要擅自删除关键注释

现有注释如果明确记录了以下内容，不应仅因为“代码已经很清楚”就删除：

- 架构决策；
- 现实业务约束；
- 已知缺陷与规避原因；
- 外部系统限制；
- 性能或安全上的特殊原因；
- 局部 Skill、AGENTS.md 或自动工具明确要求保留的结构化注释。

如果注释已经与代码事实冲突，应修正它，而不是让错误注释继续存在。

## 审查要点

修改注释时检查：

1. 这条注释是在解释“为什么”，还是只是在复述“做什么”？
2. 是否包含代码本身无法表达的约束或背景？
3. 注释是否已经随着代码变化而腐化？
4. 删除它是否会使下一位维护者失去重要决策依据？
5. 是否存在局部规则要求该注释保持特定格式或必须保留？
