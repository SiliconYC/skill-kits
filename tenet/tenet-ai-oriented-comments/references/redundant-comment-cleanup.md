# 冗余注释清理

本 reference 用于 `ai-oriented-comments` 的专项清理场景。主 Skill 负责回答“什么注释有信息价值”，本文件进一步规定仓库历史上需要保留或删除的注释类别，以及连续多行注释的清理边界。

## 描述

#### 问题描述

自 2026 年 7 月以来，本软件仓库中出现了越来越多的冗余注释。这些冗余注释一般来说都是 AI 生成的。

就目前看来，AI 出现了严重的“注释啰嗦”现象。也就是说，对于一些不言自明的简单情况，进行了毫无意义的解释。

#### 应该保留或应该删除的注释类别

结合 @SIN-3485-XzfbhDga , @PIX-3405-LVUrCtcg , @FIY-9296-c4kG9m3m , 以及一些其他相关文件的说明，特此重申一下注释的规范。

以下注释是必须保留的：

- Class 更新日志。
- 方法的参数注释和返回值注释。
- 记录代码核心意图的注释。
- 高难度 Debug 记录。
- 某些基类/子类体系中，对于抽象方法的描述。此类内容一般会被 `# region 继承重写指引` 和 `# endregion` 结构包裹。
- 注册器程序中关于注册项的注释。（删除后可能导致注册器难以维护）
- 程序文件中 `# region` 和 `# endregion` 的分区标记。

以下注释是绝对不应该保留的：

- 逐句解释语法意义。
- “同义反复式”参数解释。例如，在类型提示已经十分明确的情况下，还要追加一行注释；或者对于一些语义绝对不可能理解错的简单参数进行注释，导致简单问题复杂化。
- 简单的 Debug 记录。
- 相冲突的修改记录或 Debug 记录。也就是说，某些 Debug 过程并未彻底解决问题，反而留下了新的问题。后来正式解决此问题时，同时记录了两次或以上相冲突的修改记录。遇到这种情况，只保留最后一次修改的结果即可。
- 在生产代码中提及测试方法、测试资源。

如果你看到的一些注释并不属于以上必须保留或绝对不应保留的范畴，请根据常理判断。目前我可以明确告诉你的是，代码仓库中的注释过多了。如果你也觉得冗长，就一定要清理此处的注释。

#### 对连续多行注释的清理

根据我们的编程规范，在某些地方只允许使用单行注释。然而最近发现 AI 经常留下大量非法的多行注释。这些多行注释，绝大多数是以多个连续的行内注释的形式写出的。但少数情况下面也可能使用了多行 docstring 的写法。

特此重申，以下位置绝对不允许写真正的多行注释，也不允许使用多个连续的行内注释：

- 脚本开头的 `# ◔ 说明` 注释。此处在任何情况下都只允许写一行，而不是多行。换言之，在下方的 `# ◑ 导入` 之上只允许有一个非空行存在。
- 纯粹是担心注释太长而导致折行。在任何情况下，一句注释是不允许使用多个行内注释来拆分的。如果你担心一句注释太长，显示不完。那么你应该做的不是去拆分它，而是去精简它，让它一行能写完。
- Class 开头的更新日志，将同一条记录拆成多行——这同样是不允许的，这可以看作是上一种错误的特化版本。

如果你遇到了上面的情况，优先应当考虑简化注释。
