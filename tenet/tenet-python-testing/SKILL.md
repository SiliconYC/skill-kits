# Python 测试规范

## 核心原则

测试代码是生产代码的配套资产，必须随生产代码共同维护。不得留下过时测试，也不得通过破坏有效测试来掩盖错误。

测试执行及失败处理遵循 `tenet-repository-test-gate`。

## 测试资产的维护

- 所有测试代码与测试数据均可根据实际需要修改、移动或删除，不得无故操作。
- 生产代码变更导致测试过时时，应确认新行为正确，并同步更新测试。
- 测试已失效、重复或被有效替代时，可以合理清理。
- 严禁为了掩盖错误而删除有效测试、削弱断言或随意跳过测试。

## 测试的组织方式

### 1. 自动化测试

单元测试、集成测试等自动化测试由 AI 负责执行，测试文件按照项目及测试框架的最佳实践组织，不强制指定存放目录。

### 2. 人工测试

人工测试主要用于组件级功能验收，通过独立入口及必要的 Mock 数据，让人类能够直接运行和检查组件。

仅以下两类组件可按需设置 `人工测试/`：

- **工作站**：`G_套件/C_服务/B_工作站/` 与 `G_套件/D_交互/B_工作站/` 下的每个一级子目录，均视为一个独立工作站。
- **私有套件**：各 App 的 `私有套件/` 目录下，每个一级子目录均视为一个独立私有套件。

`人工测试/` 应建立在上述工作站或私有套件的根目录内，不得集中建立在它们的共同父目录下。

其他层级采用以下方式：

- **零件**：特指 `G_套件/C_服务/A_零件/` 与 `G_套件/D_交互/A_零件/` 中以单个 Python 文件为单位的组件。需要人工运行时，可在该文件的 `if __name__ == "__main__":` 区域提供测试入口，不单独建立 `人工测试/`。
- **App 与底盘**：使用自身的生产入口进行人工验收，不额外设置人工测试目录。

## 人工测试入口

1. 每个 `人工测试/` 目录只允许一个直接运行入口，统一命名为 `人工测试入口.py`。
2. 运行入口即可启动组件级测试环境，展示主要功能，并提供必要的模拟数据。
3. 允许设置辅助脚本和测试资源，但不得增加并列入口。
4. 测试环境必须与正式业务数据隔离，生产代码不得依赖 `人工测试/` 中的模块。
