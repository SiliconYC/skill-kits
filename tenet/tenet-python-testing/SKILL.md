# Python 测试脚本规范

## 核心定位

我们高度重视代码测试，但绝不允许多样繁杂的临时测试文件在仓库中野蛮生长。正因为重视测试，更必须对测试资产的存放边界实行严格管控。

本 Skill 的核心目的在于**测试资产与生产资产的物理隔离**，确保未来能够对所有临时性测试代码和数据进行无残留的一键批量清理。

## 适用范围与边界

- **仅约束 Python 语言**：本规范当前对 Python 编程生效，其他编程语言暂不作强制约束。
- **仅约束 AI 新建文件**：本规范约束所有由 AI 新建、生成的测试代码和测试数据。对于人类开发者已经存放在其他目录下的既有测试文件，AI 必须尊重现状，不得擅自移动、修改或删除。

## 核心隔离原则

### 1. 严格归入 `人工测试/` 目录

凡是 AI 为验证逻辑、复现问题、执行冒烟测试或辅助开发而新建的任何测试代码、临时脚本或测试数据，**必须且只能**位于名为 `人工测试/` 的根级目录之下。

- 可以直接位于 `人工测试/` 根目录。
- 也可以按需在 `人工测试/` 下建立嵌套子目录进行组织（如 `人工测试/模块A/`、`人工测试/临时数据/`）。
- 绝不允许遗漏在 `人工测试/` 之外的任何层级。

### 2. 禁止在生产目录混杂测试代码

- 严禁在生产代码所在的业务模块目录下直接创建任何测试代码。
- 严禁在生产业务脚本旁边随意新建同级测试脚本（例如在 `app/service.py` 旁新建 `test_service.py` 或 `test_临时.py`）。
- 生产目录必须保持绝对纯粹，只承载生产运行所必需的代码与静态资源。

### 3. 双向隔离：`人工测试/` 严禁包含生产代码

隔离规则是双向平等的：

- 生产目录不得包含测试文件。
- `人工测试/` 目录内**严禁包含任何生产业务代码**。
- 生产环境的任何业务模块，绝对禁止通过 `import` 反向引用 `人工测试/` 目录下的任何模块或辅助函数。

> [!important]
> `人工测试/` 本质上是一个具备完整可丢弃性的临时目录。把所有测试脚本与数据集中放置于此，唯一的设计意图就是**方便后续定期进行批量删除**。一旦该目录下混入生产代码或被生产代码依赖，批量删除将会引发生产故障。

## 人类既有测试资产的处理边界

人类开发者有时会出于架构需要，在项目根目录、独立测试框架目录或特定生产子目录下放置某些特殊的永久性测试文件或集成用例。

- 这种现象属于人类开发者的显式意图，是合法且被允许的。
- AI 在执行任务时，**严禁将此类人类创建的非 `人工测试/` 目录测试文件擅自移动到 `人工测试/` 目录下**。
- AI 同样不得以“测试文件放错位置”为由擅自清理这些历史永久测试资产。
- 只有当任务明确要求“新建”测试代码或测试数据时，AI 才必须严格执行将其创建在 `人工测试/` 之下的规则。

## 审查与自检清单

在提交任何涉及测试文件的修改前，依序检查：

1. 本次由 AI 新建的 Python 测试脚本是否全部放置在 `人工测试/` 目录或其子目录下？
2. 生产代码目录中是否存在伴随本次任务随手创建的临时测试脚本？若有，必须立即迁移至 `人工测试/` 或直接删除。
3. `人工测试/` 目录内是否误存了核心生产逻辑？是否有生产模块反向 `import` 了 `人工测试/` 内的文件？
4. 是否误动了人类开发者在其他目录下原本就存在的永久测试文件？
