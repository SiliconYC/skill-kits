# Markdown 排版与格式规范

## 适用范围

本规范适用于所有由 Agent 创建、修改或审查的 Markdown 文件。无论是日常业务文档、技术说明、需求规格，还是各类特殊的 Agent Skill 与规则文档，均应统一遵循本规范。

良好的排版旨在提升阅读者的信息获取效率，避免视觉噪点与无谓的版面割裂。

## 严格的空行规范

空行是 Markdown 语法解析和视觉分块的基础契约。必须遵循标准的空行使用准则，既不能缺少必要空行，也不得滥用多余空行：

- **标题周围必须留空**：任何级别的标题（`#` 至 `######`）下方必须保留一个空行，严禁正文、子标题或列表紧贴在标题下一行；标题上方除位于文档开头或紧随 Front Matter 外，也必须保留一个空行与前文隔开。
- **列表首尾必须留空**：无论是无序列表（`-`）还是有序列表（`1.`），列表第一项之前、列表最后一项之后，都必须各保留一个空行，明确区分列表与上下文段落。
- **代码块周围必须留空**：多行代码块（```）的前后，必须各有一个空行，不得与相邻段落紧密相连。
- **引用与 Callout 周围必须留空**：标准引用块（`>`）与 Callout 提示块的前后，必须各有一个空行隔开。
- **严禁多余连续空行**：文档中任意两个结构之间最多只允许保留一个空行，严禁出现两个或以上的连续空行。

## 列表符号统一

在编写 Markdown 无序列表时，严格统一使用中划线（减号 `-`）作为行首标记符号。

- 正确写法：使用 `- 列表项内容`。
- 错误写法：禁止使用星号 `*` 或加号 `+` 作为无序列表的起始标记。
- 在嵌套无序列表中，同样保持使用中划线 `-`，依靠缩进区分层级，不混用星号。

## 文本强调与加粗边界

不排斥对关键信息进行加粗，但应杜绝滥用加粗与大段加粗。

- **精准加粗**：仅对核心结论、关键术语、状态词（如“立即停止”、“必须”）或句首主题词进行加粗，起到引导视觉锚点的作用。
- **避免整段加粗**：整句话或连续多句话加粗会破坏排版层次，降低真正关键信息的辨识度。如果整段内容都很重要，应通过提取标题、使用列表或借助 Callout 提示块呈现，而不是直接通篇加粗。
- **避免滥用**：一屏或一个章节内不宜出现过于密集的加粗词汇，保持版面清爽。

## 节制使用分割线

除了文档开头用于包裹 YAML 元数据（Front Matter）所必需的分割线（`---`）之外，正文内文应尽可能节制，原则上避免使用分割线。

- 分割线容易造成版面视觉碎片化，破坏长篇阅读的连贯性。
- 内容分块与逻辑流转应优先依靠清晰的 Markdown 标题层级（`##`、`###`）或空行进行自然区隔，而非机械插入横线。

## 程序相关概念使用行内代码块

在正文提及任何与程序、系统、指令或文件系统相关的概念时，必须使用单反引号（`` ` ``）包裹成行内代码块：

- **文件与路径**：如 `README.md`、`.gitignore`、`tenet/tenet-python-general/`。
- **代码标识符**：类名、函数名、方法名、变量名（如 `示例_类`、`api_读取()`、`arg_字典`）。
- **配置与键名**：JSON/YAML 字段名、环境变量、配置参数（如 `name`、`PATH`、`.env`）。
- **命令行指令与参数**：如 `git switch -c dev`、`--default-branch`。

反引号包裹不仅能够明确上下文语境，还能防止特殊符号（如下划线 `_`、星号 `*`）被 Markdown 误解析为斜体或格式标记。

## 标准 Callout 语法

当需要突出显示补充信息、建议、警示或关键约束时，统一支持并使用以下四种标准 Callout 语法。每种 Callout 都有明确的语义场景，请根据信息严重程度准确选用：

### 1. 补充说明：`> [!note]`

用于补充背景信息、概念定义或延伸说明，属于中性提示。

> [!note]
> 这里是补充说明内容。用于记录不影响主流程但有助于理解全局的背景事实。

### 2. 技巧与建议：`> [!tip]`

用于提供最佳实践、操作捷径、优化建议或使用提示。

> [!tip]
> 这里是操作建议。提示维护者如何更高效地完成当前目标或规避潜在繁琐步骤。

### 3. 风险警告：`> [!warning]`

用于提醒容易踩坑的边界情况、不可逆操作的前置提示或潜在副作用。

> [!warning]
> 这里是警告信息。提醒操作者注意潜在破坏性风险或容易被忽略的约束。

### 4. 关键原则与硬性约束：`> [!important]`

用于强调必须绝对遵守的硬性规则、机器契约或不可违背的底层设计准则。

> [!important]
> 这里是核心约束。该内容属于必须严格落实的底线规则，后续维护者不得擅自绕过。

## 审查核对清单

生成或修改 Markdown 文本后，依序自检：

1. 标题（`#` 至 `######`）下方是否均保留了一个空行？
2. 无序列表与有序列表的首尾是否均留有一个空行与前后文隔开？
3. 代码块及 Callout 提示块前后是否均留有单个空行？
4. 文档内是否存在连续两个或以上的冗余空行？
5. 无序列表是否全部使用中划线 `-`，是否存在残留的 `*` 列表？
6. 加粗是否克制，是否存在整句、整段大面积加粗的情况？
7. 正文内部是否存在不必要的分割线（`---`）？
8. 涉及的所有文件路径、变量名、类名、配置字段是否均使用了行内代码块包裹？
9. 如有使用提示块，其类型是否严格符合四种标准 Callout（`note` / `tip` / `warning` / `important`）语法？
