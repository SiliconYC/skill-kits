# 本地 AI Agent 的 Git 分支工作流

接手任务准备修改代码前，你的第一件事是判断当前物理工作区的身份，再判断它处于哪一个 Git 分支。不同工作区与分支决定了后续应该在哪里开发、如何提交、是否需要合并、以及是否需要同步到 GitHub。

## 主工作区不可侵占原则

> [!important]
> **禁止切换受保护主工作区的分支。** 

以下工作区被视为受保护的工作区：

- Git 主工作区（`git worktree list --porcelain` 中的主工作树）。
- 该工作区中的 Git 分支名为 `main`、`dev`、`smart` 或 `golden-gate`。（这四个是本公司指定的核心永久分支）
- 与 Git 仓库同名的本地目录。

以上工作区中的 Git 分支必须保持固定。

例如，硬盘上的某个目录被固定在 `dev`，就绝对不能在该目录执行 `git switch -c`、`git checkout -b` 或任何会把它切换到其他分支的操作。

当你需要对这些工作区进行修改时，应该这样做：

- **物理隔离**：从受保护主工作区发起开发任务时，必须通过 `git worktree add -b` 新建独立物理目录与临时分支。禁止在主工作区原地切换到临时分支开发，也禁止直接修改、提交永久分支上的开发性代码。
- **保持干净**：受保护主工作区只用于检查状态、同步已完成的提交，以及在验证后快进更新永久分支。开发、测试产生的修改和合并冲突不得留在这里；不得将它作为任务草稿或冲突解决现场。一个最简单的判断标准是：主工作区中永远不能有代码位于 Git 暂存区。
- **异常不得合理化**：若受保护主工作区已经处于临时分支、游离 HEAD 或含有未提交修改，应视为异常，停止常规开发，查明并安全保全现场，向用户报告或按用户明确给出的恢复指令处理。绝不能因为当前分支是临时分支，就直接执行工作流 B；不得擅自 `reset --hard`、`clean -fd`、`stash`、强制切分支或删除修改。

## 第一步：识别当前工作区身份与分支

执行 `git rev-parse --show-toplevel`、`git worktree list --porcelain`、`git branch --show-current` 和 `git status --short`，先核对当前工作区的真实路径、它是否是 Git 主工作区或用户指定的受保护目录，再将当前分支归入以下两大类之一（若处于无分支名的游离 HEAD 状态，直接停下来询问用户）：

1. **四大永久分支**：`main`、`dev`、`smart`、`golden-gate`
2. **非永久分支（现成临时分支）**：除上述永久分支以外的所有分支

首先服从用户或项目给主工作区指定的固定分支；若未指定，则以正常接手时该目录所在的永久分支为固定分支。若主工作区已处于临时分支，不得反过来把该异常分支认定为它的固定分支。确认工作区身份与分支分类后，严格按对应的工作流执行，无需向用户请示常规步骤，仅在异常或无法安全解决的冲突时中断。

## 工作流 A：当前位于【四大永久分支】

`main`、`dev`、`smart`、`golden-gate` 均在 GitHub 上有远端备份，要求本地与 GitHub 保持严格同步，且**禁止直接在永久分支上开发和提交代码**。从永久分支发起任务时，原工作区必须留在原分支，所有开发必须转移到独立 Worktree。

当你发现当前工作区处于这四个永久分支之一时，必须按以下顺序自动走完全流程：

1. **拉取 GitHub 最新代码**：先检查原工作区是否有未提交的修改。
   - 若工作区干净，执行 `git pull --ff-only` 同步原永久分支；不得为同步而切换它的分支。
   - **冲突中断点**：若工作区原本就有未提交的修改，立即停下来确认来源，不得擅自丢弃、暂存（`stash`）或覆盖已有修改。
2. **派生独立 Worktree**：基于同步后的原永久分支，用 `git worktree add -b tmp/<任务简述> <独立目录> <原永久分支>` 创建新的物理目录和本地临时分支。路径和分支名须唯一，避免多 Agent 互相占用。**不得用 `git switch -c` 在原工作区派生分支**。
3. **在自建 Worktree 中开发与测试**：只在新目录内编程、测试和本地提交（`git commit`）。该临时分支仅作本地过渡使用，**严禁将其推送到 GitHub**。原工作区始终留在原永久分支上。
4. **隔离合并与验证**：测试通过后，从原永久分支的最新状态再创建独立的集成 Worktree 和集成临时分支，在该目录中合入任务分支、解决冲突、完成必要测试。合并与冲突处理均不得发生在受保护主工作区。若远端或原永久分支已被其他 Agent 更新，先在集成 Worktree 中纳入最新变更并重新验证。
5. **主动合回原永久分支并同步 GitHub**：确保原工作区干净且永久分支没有发生未经核对的变化，以单写入者方式将已验证的集成分支快进合入原永久分支（例如 `git merge --ff-only tmp/<集成任务>`），随后执行 `git push`。从哪个永久分支派生，就必须交还给哪个永久分支；**整个过程不需要切换原工作区的分支**。
6. **收口清理与交付验收**：确认远端推送成功、原工作区仍在原永久分支且 `git status --short` 为空，再依次删除已经完成、且无未提交修改的任务及集成 Worktree（`git worktree remove`），之后删除对应本地临时分支（`git branch -d`）。最后才通知用户检测验收。

- **并发保护**：多个 Agent 同时完成任务时，必须串行执行对同一永久分支的最终更新与推送，并在操作前重新核对本地及远端提交位置。若更新期间分支发生变化，回到隔离集成环节重新合并、验证与重试；不能保证独占写入时，不得冒险覆盖别人提交。
- **冲突中断点**：若合并冲突无法安全自动解决、快进失败或推送因远端变化被拒绝，先保留任务和集成 Worktree，尝试在隔离目录核对最新版本并解决；仍无法安全完成时再报告用户。严禁使用 `--force` 强制推送，不得让受保护主工作区留有未提交的冲突文件或半成品。

> [!warning]
> 严禁停在自建临时分支上让用户验收，也严禁把受保护主工作区留在临时分支上。开发、测试、合并、推送及工作区清理全部完成后，才算任务收口；如果中途断线，未完成的工作保留在独立 Worktree 中，原主工作区仍应保持原永久分支和干净状态。

## 工作流 B：当前位于【非永久分支（现成临时分支）】

当你接手工作区时，发现它位于一个非永久分支，而且已核实它是**独立的、未受保护的临时 Worktree**，说明用户直接交给你的是一个局部开发环境。这类分支通常没有在 GitHub 上同步，贸然同步也没有意义。若当前路径其实是主工作区，则属于前述异常，绝不能套用本流程。

请忽略其他分支的存在，直接按以下规则处理：

1. **直接接手现有代码**：直接在当前独立 Worktree 已有的代码基础上进行编程开发，保留工作区原有的合理改动。
2. **本地测试与原地提交**：编程和测试完毕后，直接将代码提交（`git commit`）到当前工作区所在的这个临时分支即可。
3. **不派生、不合并、不同步**：除非用户另有明确指令，否则**不需要**再派生新分支，**不需要**与其他任何分支合并，也**不需要**拉取或推送到 GitHub。本地提交完成后，即可直接通知用户检测验收。

## 核心行为对照表

| 接手时的工作区与分支 | 是否拉取远端 | 开发与提交位置 | 是否合并 | 是否推送到 GitHub | 最终交付状态 |
| --- | --- | --- | --- | --- | --- |
| **永久分支**（`main` / `dev` / `smart` / `golden-gate`） | 原工作区干净时同步 | 新建独立 Worktree 开发、测试与提交 | 在独立集成 Worktree 验证，原永久分支只快进接收 | 推送原永久分支，临时分支绝不推送 | 原工作区始终位于原永久分支且干净；清理临时 Worktree |
| **独立的现成临时 Worktree** | 不拉取 | 当前临时 Worktree 原地开发、测试与提交 | 不合并 | 不推送 | 保持当前临时分支，直接通知用户验收 |
| **受保护主工作区异常处于临时分支或存在未提交修改** | 暂停 | 不得继续开发 | 不执行常规合并 | 不推送 | 保全现场，按明确恢复指令处理，不得误用工作流 B |
